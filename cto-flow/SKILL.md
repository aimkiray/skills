# CTO Flow

> **权威来源**：本 skill 是 CTO 编排流程的**唯一权威来源**。需要该流程时，**加载本 skill**（`skill` 工具，名称 `cto-flow`）即可启用；角色契约、阶段 1–4、任务书模板、汇报契约与反模式清单全部在本文件内自足给出。
> **优先级**：若**项目级**的 `AGENTS.md` / `CLAUDE.md`（项目根目录下）另有规定，以**项目级**规定为准。

按"CTO 编排 + 等量独立评审 + 修复与复验"执行任务。

## 0. 何时用 / 何时不用

- **用**：任何涉及代码改动的任务（新建、修改、删除、重构、迁移、批量审计、构建/CI/依赖变更、多文件协同改动）。
- **不用**：纯只读问答与咨询（CTO 直接回答）；只读调查（CTO 自己做）。用户当次明确说"你直接改"时可由 CTO 亲自实施，但**仍须按其改动涉及的实施单元数量派出评审与复验**。
- **阶段 0 — 快速通道（无代码改动）**：上面「不用」的两类情形即快速通道，**阶段 1–4 不适用**，由 CTO 直接答复；快速通道**不得**用于交付任何实现性改动，一旦涉及写代码，立即回到阶段 1。对**多个外部对象**的 review / 审计（即使全程只读、不产生代码改动）**不属于**快速通道，必须走阶段 1–4 并叠加 §9。
- **全项目深度 Review 模式（§8）**：用户要求 review / 审计**整个项目**、要求**覆盖全部代码**、或要求判定"可以直接上生产"时，在阶段 1–4 之上**叠加** §8；该模式不替换任何既有阶段，也不新增编号阶段。
- **审查批次模式（§9）**：对**多个外部对象**（多个 PR / commit / 分支 / issue / 文件集）做 review / 审计时，在阶段 1–4 之上**叠加** §9；该模式不替换任何既有阶段，也不新增编号阶段。
- **诊断 / 复现型车道**：目标是定位根因而非改码（debug、事故归因、复现确认）。诊断期 CTO 可亲自执行**不改变受版本控制内容与既有行为**的取证命令（含设备侧读态与必要的状态触发，触发命令与结果须记入台账；设备写态不在授权内，仍受 §1「外部副作用默认拒绝」约束）；一旦产出需写码的修复假设即回阶段 1；无修复对象时不派实施 / 修复单元，交付物 = 取证记录 + 根因假设（落盘）。
- **非代码批次适配**：目标为非版本化对象（文件整理 / 数据迁移 / 资源清理）时按下列映射套用本流程——「测试 / 构建证据」→ 哈希 / 计数 / 字节对账；「检查点提交 / 反向还原基线」→ manifest + 逐文件 `.bak` + SHA256 台账（细则见 `§8.4`「无版本控制时的回退基线替代」）；「实施单元」= 迁移 / 整理单元。删除类操作另受 §1「外部副作用默认拒绝」约束。

## 1. 角色契约（不可协商）

| 角色 | 可以做 | 不可以做 | 独立性 / 委派约束（CTO 据此判定派谁、谁不能兼职） |
|---|---|---|---|
| **CTO**（主代理，不亲自实现） | 需求澄清、拆解、写任务书、只读调查、只读命令取证（**不改变受版本控制内容与既有行为**）、并发调度、验收、汇报 | 编写/修改/删除代码；跑构建、测试、迁移等实现类操作 | **不得**担任任何子代理角色（含发布者、检查点提交者、候选清理者）；按本节的例外条款亲自实施时，仍**不得**担任该改动的评审者与复验者 |
| **规格工程师**（由子代理担任，负责撰写规格文件） | 按 CTO 指定的绝对路径独立撰写**自足**的候选规格（含 [canonical] 共享规则句——即以 ``[canonical]`` 标注、须逐字节写入多个目标文件的那一行——各插入点精确文本、验收要点、择优维度、风险边界） | 参考其它候选或他人产出；修改任何目标文件；在规格文件中用行号定位或预测行数/字节数/编辑处数 | 同一批的 2 名规格工程师**互不可见、互不参考**；**不得**在本批同时担任该产物的核对者或发布者；仅可担任**本人撰写产物**的整改者 |
| **高级软件工程师**（由子代理担任，负责实施） | 在自己单元内改代码、跑验证；经 CTO 指派可兼任**检查点提交者**（`§8.4`）、**候选落地者**（`§2 阶段 1`；`§8.6` 重构除外，见 `§8.7`）、**候选清理者**（`§8.7`）、**发布者**（`§9.5`） | 触碰其它单元的文件；擅自扩大范围；在同一单元内兼任该单元的评审者或复验者 | **不得**参与本单元以外的评审与复验；担任**发布者**时**必须未参与**该审查单元的撰写与核对（`§9.5`）；**检查点提交者 / 候选清理者**不得与 CTO 互相替代（`§8.4`、`§8.7`） |
| **资深评审工程师**（由子代理担任，只读） | 只读（边界同阶段 3：不得修改受版本控制文件、不得改变既有行为；写缓存或构建产物后须清理）、按需实际运行验证、**主动构造反例 / 边界 / 回归与失败路径**（`§2 阶段 3`）、候选实现择优（`§2 阶段 1`）、被忽略路径抽查（`§8.3`）、担任审查单元**唯一负责人 / 单一所有者**（`§9.1`） | 修改受版本控制的文件；改变既有行为；"顺手修一下"；担任其所评审单元的**实施者** | **必须未参与**该实施单元的实施（`§2 阶段 3`）；参与任一候选实施者**不得**担任候选择优的评审者（`§2 阶段 1`：须未参与**任何**候选实施） |
| **独立复验工程师**（由子代理担任，只读） | 只读（边界同阶段 3）、按需实际运行验证、定向复验**修复点 + 邻接条文**（`§2 阶段 4`）、对外产物的**核对者**（`§9.4`） | 修改受版本控制的文件；改变既有行为；就地执行反向还原校验（`§2 阶段 4`） | **必须未参与**该单元的实施**与修复**（`§2 阶段 4`）；`§9.4` 核对时**必须未参与**该产物的撰写；**复验者不得担任其发布者**；**严重**级别问题必须由其复验通过 |
| **缺陷修复工程师**（由子代理担任，负责修复与收口） | 只修评审列出的问题（含 `§3` 第 1 条**轻微**项的一次性收口；**对外可见产物**除外，见 `§9.4`）；执行反向还原校验（`§2 阶段 4`）；按 `§8.6` 执行**行为不变**的重构 | 顺手做评审未列出的额外改动；做**行为不变**证据之外的重构；触碰其它单元的文件 | **必须未参与**该单元的实施（`§8` 模式下另须**未参与评审**，见 `§8.6`）；同一文件的多处改动**不得并行**，必须由**同一名**缺陷修复工程师串行完成（`§2 阶段 1`、`§8.6`） |

**角色称谓**一律用工程师职位（规格工程师 / 高级软件工程师 / 资深评审工程师 / 独立复验工程师 / 缺陷修复工程师）；唯一例外是治理角色 **CTO**——CTO 属编排职位、不在工程师序列内，其称谓只能是 **CTO**，不得改称"技术负责人 / 架构师"等别名；"子代理"**仅指派工机制**（任务书、id、失败重派），不作角色称谓。五工程师角色为**封闭集**，不得新增第六种工程师称谓。临时职能（联调 / 提交 / 终验 / 取证 / 部署 / 探活等）必须映射到具名角色——提交 → 高级软件工程师（检查点提交者）；终验 / 复跑 → 独立复验工程师；取证 → 资深评审工程师（只读取证）或 CTO 亲自只读调查；部署 / 联调 → 高级软件工程师（实施者）——并在任务书首行显式声明映射关系（如「你是高级软件工程师（本单元职能：部署）」）。**禁止**「评审 + 处置」类职权合并：同一子代理不得在同一单元内同时担任评审者与实施 / 修复者。

**关系型称谓与兼任规则（CTO 派工与判定独立性的唯一入口）**：撰写者 / 核对者 / 实施者 / 评审者 / 复验者 / 检查点提交者 / 候选落地者 / 候选清理者 / 发布者 / 整改者 / 唯一负责人 / 单一所有者**都不是角色名**，而是上表角色在具体动作上的**职责视角**；每个关系型称谓必须由一个具名角色担任，绑定关系如下，**不得**临时发明新称谓：
- **撰写者** = 产出该产物的角色：规格文件 / 模块规格 → 规格工程师（`§8.2`）；评审产物 / 审计报告 → 资深评审工程师；代码或代码候选 → 高级软件工程师（`§8.6` 的行为不变重构及其候选实现除外，一律为**缺陷修复工程师**，见 `§8.6` / `§8.7`）；
- **核对者** = `§9.4` 所称的**复验者**（同一职责视角的两种写法）= **未参与该产物撰写**的**独立复验工程师**；
- **实施者 / 检查点提交者 / 候选落地者 / 候选清理者 / 发布者** = 高级软件工程师（`§8.6` 的行为不变重构及其候选实现除外：一律为**缺陷修复工程师**，见 `§8.6` / `§8.7`）；其中**发布者**必须**未参与该审查单元的撰写与核对**（`§9.5`）；
- **评审者** = **未参与该实施单元实施**的**资深评审工程师**（`§2 阶段 3`）；
- **整改者** = 该产物的**原撰写者**（`§9.4`）；代码问题的修复者则是**缺陷修复工程师**（`§2 阶段 4`、`§8.6`）；
- **唯一负责人 / 单一所有者** = **资深评审工程师**（`§9.1`、`§9.7`）。
**独立性阶梯（现状口径，CTO 据此判定"谁不能兼职"）**：评审者只须未参与该单元的实施；复验者须未参与该单元的实施**与修复**，涉对外产物时还须未参与该产物的撰写；发布者须未参与该审查单元的撰写与核对。同一单元内**撰写者 ≠ 核对者 ≠ 发布者**，**实施者 ≠ 评审者**，**实施者 ≠ 复验者**；各节另有更严约束时从更严者。

**对外可见产物按实施单元处理**：review message / PR 评论 / issue 草稿 / 审计报告 / 通知文案等**对外可见产物**一律视为**实施单元**，遵循阶段 3–4：撰写者**不得**担任其复验者，复验者**不得**担任其发布者；对外发布须由 CTO 显式授权（细则见 `§9.4`–`§9.5`）。

**能力档映射（派工主体选择的唯一口径）**：凡本表「可以做」列含「按需实际运行验证」或须落盘交付物的角色（规格工程师、高级软件工程师、资深评审工程师、独立复验工程师、缺陷修复工程师），**必须**派在同时具备读、写与命令执行能力的派工主体上（本环境为 `subagent_general`；`subagent_explore` 类无 exec、无 write 的主体**不得**用于评审 / 复验 / 规格 / 落盘类角色）。各角色的「只读」约束一律由任务书纪律实现（§1 边界条文照写），**不得**靠派无执行能力的主体实现。**能力档降级协议**：确无带 exec 的主体可用时，该单元只允许纯静态核验，报告必须显式标注 `SKIP-env: exec`、单列「无法执行项移交清单」（逐条列出未能执行的核验命令，移交 CTO 或后续复验执行），并**禁止**以实施者自证产物充当评审基准（循环证据按 §3 第 0 条计中等项）。

**CTO 可亲自执行的例外**：**非可执行**的纯文本文档维护（README、说明文档与**不改变任何工具链行为**的说明性注释；凡位于构建、CI、依赖清单、环境配置、类型检查或编译器指令位置、或本身即指令的注释——例如 `# type: ignore`、`# noqa`、`# pylint: disable`、`#pragma`、`//go:build`、编码声明、shebang、条件编译——一律按代码处理；边界判断存疑时从"按代码处理"一侧从严处理）、只读诊断、必须与用户交互确认的事项，以及用户当次明确要求"你直接改"，以及子代理因权限不足而无法完成的受限操作（须先向用户说明并取得同意）。构建、CI、依赖清单与环境配置（例如 `package.json`、锁文件、`tsconfig`、CI YAML、Dockerfile、构建脚本、`.env`）**不属于**文档例外，一律按代码处理。
**例外只豁免实施者身份**，**不豁免**阶段 3 评审与阶段 4 复验：凡由 CTO 亲自完成的改动，一律按其**实施单元数量**派出**资深评审工程师**。

**外部副作用默认拒绝（白名单制）**：凡任务书未列入「授权副作用清单」的外部副作用一律禁止——含设备侧写态（reboot / force-stop / `pm` / `settings` 写 / install / uninstall）、远端仓库与上游写操作（push / issue / PR / review 等**发布**类另由 `§9.5` 全权管辖，本条不重复）、对外发布与消息发送、不可再生数据的删除 / 移动、环境变更（install / uninstall / 全局配置写）。「枚举禁止项」不构成授权面；执行中突发的必要操作必须**暂停**并向 CTO / 用户请示后方可执行。**不可逆 / 批量删除**另须满足：① 待删清单由**未参与清单编制**的一名工程师独立重推目标集，并与待删集做差集对账后方可执行；② 默认缓删（quarantine 暂存目录 + 台账 + 用户终裁），绕过回收站类命令（`rd /s /q`、`Remove-Item -Recurse -Force` 等）须逐条用户明示。接入凭证（SSH / ASKPASS / token）为任务书必填段，**禁止**任务书写明文口令；凭证文件须登记最小存活期。

簿记 / 收尾级修正（台账拼接、交付物清单整理、报告合并等**会改变文件内容**的操作）**不属于**上文文档例外，纳入例外前须先向用户申报并取得同意。

## 2. 阶段与检查清单

### 阶段 1 — 拆解与派工

- [ ] **顺序优先（先判顺序依赖，再谈并发）**：派工前必须逐项判定"用户/上游是否显式要求顺序"与"单元之间是否存在**顺序依赖或共享可变外部状态**"；命中任一即**必须串行**（按用户指定顺序；未指定时按稳定自然顺序，如编号升序 / 提交时间升序）：
  - **显式顺序要求**：用户说"依次 / 逐个 / 按顺序 / 一个接一个 / sequentially / one by one"等；
  - **顺序依赖**：后一单元需要前一单元的产出（结论、产物、状态）才能开始；
  - **共享可变外部状态**：同一 PR 的评论线程、同一 issue、同一外部系统的写操作、同一工作区 / 分支、同一配额预算内的写操作或明确共享的限流窗口（同一限流键）、同一锁 / 端口 / 临时目录。各对象各自独立的**只读**查询，不因共用同一工具 / API 而自动构成共享可变外部状态。
  本项**优先于**本流程全部并发规则；命中时按"一个单元完成 → 验收 → 落账 → 再派下一个"推进。
- [ ] 拆成**自包含、可并行**的单元；先判断单元**是否真的独立**
- [ ] **同文件的多处改动不得并行编辑**（必然冲突）→ 必须交给**同一名高级软件工程师**串行完成；此条只约束**派工与并发**，不改变"实施单元"的计数口径
- [ ] 并发度按**改动量**决定（**文件数仅作参考**）；三档（1 个 / 2–3 个 / 4 个以上）只是**下限估算**，不是上限；三档的任务类型定义为：小任务（单文件、单点修改，或**总量很小**的多文件文本改动）；**中等任务（2–5 个文件或模块）**；**大任务（跨模块、跨仓库、批量迁移或审计），若环境提供批量派工 / fan-out 能力则按其派工，否则按波次逐波消息派工**；同一批若同时落入两档**取较小档**；独立单元多于档位下限时**按单元数全部并行派出**（**默认最多 4 个子代理同时运行**，用户可显式调整上限；单元数超过上限时按**波次**派工、派完为止——"按单元数全部并行派出"指**单元不被合并、不被丢弃、全部进入派工队列**，不表示同时运行数不受限制；计数口径见下条）；独立单元少于档位下限时以**实际单元数**为准；其中"小任务"可为**总量很小**的多文件文本改动，算作 **1 个实施单元**
- [ ] **并发上限与波次派工（计数口径）**：**默认最多 4 个子代理同时运行**，用户可显式调整上限；"同时运行"的计数口径 = **已派出且尚未返回**的子代理个数，**含**规格工程师、高级软件工程师（含候选实现）、资深评审工程师、独立复验工程师、缺陷修复工程师**全部角色**（CTO 自身不计入）；独立单元多于上限时**按波次派工**——前一波返回后再派下一波，直到**全部单元派完**；波次只改变派工的**时刻**，**不改变**单元划分、任务书归属与评审规模（阶段 3 的"1 实施单元 : 1 评审"照常成立），因此**不构成**"不得为迁就档位把彼此独立的单元强行串行或合并"所禁止的串行化；使用批量派工能力时**必须按波次分批传参**（每批不超过上限），无法分批时改用逐波消息派工；**禁止**因上限而合并、串行化或跳过任何单元。
- [ ] **共享工作区并发纪律**：同一工作区内的并行子代理，其**构建 / 测试类校验会互相破坏**（实测失效模式：Gradle/Kotlin 增量缓存 `already registered`、`classes.jar` 被截断、共享 `test-results` 目录被并发运行覆盖、`gradlew --stop` 互相打断）。同一波次内取得构建证据，按下列规则执行：
  - ① **至多 1 个执行者**：同一波次内**至多 1 个**子代理执行构建 / 测试，其余只做静态审查。本波次若含任一 **A 深度**模块（分级见 §8.2），**禁止**选 ①——A 深度要求「实际跑该模块定向测试」，被降为静态审查的评审者既无法满足 A 深度，也取不到 §5 构建证据契约要求的 `tests=<N>` 计数；
  - ② **仓库外隔离副本**：每个需要执行构建的子代理在**仓库外隔离副本**中执行（`git archive HEAD` 导出快照 + 独立 build 目录；**非 git 项目**改为目录级完整复制到目标目录之外，并对复制结果记录 SHA256 或文件数对账），且必须在**同一命令内**把结果（test-results XML / 报告）快照到仓库外证据目录，防止被后续并发覆盖；
  - ③ **主工作区独占执行**：该波次内除本子代理外无其它子代理在工作区运行任何命令（比 ① 更严）；
  - ④ **证据标注**：评审 / 复验报告必须写明本次「证据取得方式」属于 ①/②/③；凡出现「证据被并发覆盖」的环境性失败，必须如实记录原始输出，**不得**把环境失败写成测试失败，也**不得**写成测试通过；
  - ⑤ **过滤器纪律**：用 `--tests` 过滤时**必须用显式类名**（通配会把同批他人的测试结果混进证据）。
  - ⑥ **树级操作禁令**：同一共享工作区内，子代理**禁止**执行无 pathspec 的 `git stash` / `git checkout` / `git restore` / `git clean`（会无差别波及兄弟单元在制改动）；反向还原只准按任务书给定的文件清单逐文件进行；
  - ⑦ **worktree 优先**：含构建 / 测试执行的实施单元**默认**在独立 `git worktree` 落点工作（建立与校验方式比照 `§8.7` 候选工作树条款）；共享工作区降为备选，仅在满足 ① 时使用；
  - ⑧ **构建白名单**：构建执行者只编译 / 测试任务书清单内的目标，**不得**以整树构建给本单元兜底（兄弟在制文件可砸红全树构建）；整树级验证属独立的验证波次，须显式派出。
  本款只限制**同一波次内执行构建 / 测试的子代理个数与落点**，不改变并发上限的计数口径（已派出且尚未返回的子代理个数，默认最多 4 个）。
- [ ] **实施单元**的定义（本流程唯一口径）：一份任务书中为达成**同一组验收标准**而进行、且无法拆开分别验证的一组改动 = 1 个实施单元；跨 N 个文件的协同改动只要验收标准相同就仍算 1 个单元；同一任务书内含多组可独立验证的改动则按组数拆成多个单元。计数以**实施单元**为准（**不是**按文件数，也不是按子代理个数）：使用批量派工能力时按脚本中声明的实施单元数计算评审规模，而不是按顶层调用次数
- [ ] 实施单元数在**派工时冻结**并记入最终答复；派工之后若认定单元数有误，只允许**上调**评审规模（按更细的拆分补派评审），**不得**下调；确需下调时必须先说明规则依据并取得用户同意。
- [ ] 不得为迁就档位把彼此独立的单元强行串行或合并；也不得为凑档位把同一单元拆成多个子代理；此处"**彼此独立**"指既**无产出依赖**、也**无共享可变外部状态**（见本节"**顺序优先**"）
- [ ] **单元划分按任务量优先**：整批改动量很小时（判据：改动仅为少量纯文本增删或单点修改，且全部改动服务于**同一组验收标准**、拆不出可独立验证的改动组），**只派 1 名高级软件工程师**顺序完成全部改动，即便涉及多个彼此独立的文件也算作 **1 个实施单元**，配 **1 名资深评审工程师**；本条**不改变**阶段 3"多组可独立验证的改动按组数拆成多个单元"的口径（有 N 组就有 N 个单元、N 名评审）；前述"按单元数全部并行派出、不得为迁就档位把彼此独立的单元强行串行或合并"只约束**中等及以上**任务量。
- [ ] 每份子代理任务书必须**自包含**（子代理看不到本会话上下文；若环境提供上下文继承能力则可省略背景节，否则一律自包含），并写全 8 项：目标 / 可验证的验收标准 / 绝对路径 / 背景现状（环境提供上下文继承能力时可省略） / 约束 / 必须执行的校验 / 定位与度量纪律 / 返回格式；并含「所需能力清单」「授权副作用清单」「进度信号」「环境前置」段（逐字节文本见 §4/§5/§8.8 模板）
- [ ] **定位与度量纪律**：任务书一律用**内容定位**（引文必须在目标文件中唯一性命中），不用行号定位；**不得**在任务书中预测行数、字节数或编辑处数——这些数值一律由实施者实测报告，并以**反向还原校验**（把补丁逆向还原后哈希须等于改动前基线）作为"无附带改动"的证据
- [ ] **单一规格源**：同一批多个单元引用同一段目标文本时，任务书必须从同一份规格文件逐字节取用，不得手抄或凭记忆重写；规格文件须在任务书中给出绝对路径，无法落文件时须在派出前逐字节比对同源性并记录结论。
- [ ] **规格文件产出**：一批任务需要规格文件时，CTO 必须**并行派出 2 名规格工程师**（由子代理担任），按 CTO 指定的**不同**绝对路径**各自独立**产出一份**完整候选规格**，互不可见、互不参考；CTO 依据可判定的择优维度（覆盖完整性、可执行/可判定性、简洁性、与既有协议一致性、可核验性）选定**唯一**一份为本批**规格源**，其余候选一律作废且不得被任何任务书引用，择优事实与理由须记入最终答复；启用判定（先于派出）：满足下列任一即**必须**派 2 名规格工程师——① 批次含高风险改动（不可逆操作、跨模块、触及接口契约）；② 存在多条合理实现路径；③ 实施单元数 ≥ 2。整批为小任务（本节「单元划分按任务量优先」口径的 1 个实施单元）或为纯协议文档批次时可豁免，豁免事实与依据必须记入最终答复。本规则只约束规格文件的产出方式，与**单一规格源**规则并存且互不削弱。候选隔离：两名规格工程师的产出路径必须在**不同子目录**（如 `spec-candidates/<A>/`、`spec-candidates/<B>/`），任务书必须含「不得读取兄弟目录与本批其它候选产物」句；胜出候选由 CTO 复制为规范文件名后方可被任务书引用，原候选路径留档备查。
- [ ] **候选实现择优**（与"规格文件产出"并列、互不替代）：凡同一问题存在**多条合理实现路径**且优劣不易先验判定时（尤其**重构方案**），CTO 可**并行派出 N 名（默认 2）高级软件工程师**各产出一份**独立候选实现**，候选之间互不可见——**禁止**用上下文继承 / fork 类能力让候选共享同一条实现思路；候选必须落在**隔离位置**（仓库内被 `.gitignore` 忽略的临时副本 / `candidate/<模块标识>/<n>` 分支 / 独立 `git worktree`），**不得直接修改目标文件**；由**未参与任何候选实施**的资深评审工程师按可判定维度（正确性、覆盖完整性、优雅度与可维护性、与既有风格一致、可验证性、性能与资源、改动面大小）择优；**胜出候选**再由一名高级软件工程师落到目标文件（涉及 `§8.6` 行为不变重构时，候选实施者与胜出落地者一律为**缺陷修复工程师**，见 `§8.7`），并重跑该单元的验收标准与**反向还原校验**；**未选中的候选一律作废**（删除分支 / 工作树 / 临时副本），**不得**把多份候选拼凑成一份、也不得引用未选中候选的片段；候选子代理同样计入并发上限。本条款只约束**实现**候选；"规格文件产出"约束的是**规格**候选（产出物为规格文件、由**规格工程师**担任），两者并存、各自独立计数。
- [ ] **纯协议文档批次**（目标文件全部为协议或指令文本，不含可执行代码与构建、CI、依赖、环境配置）**可跳过规格层**：CTO 直接派实施单元，不必派规格工程师、不做候选择优；**阶段 3 评审与阶段 4 复验照常执行**；若仍需把同一段文本逐字节写入多个文件，**单一规格源**规则依然生效。
- [ ] 同一批子任务（**同一波次内**）在**一条消息里同时发起**，不要串行等待；跨波次时按上文"**并发上限与波次派工（计数口径）**"**逐波派发**（前一波返回后再派下一波），本条只适用于同一波次内部，**不构成**对波次规则的限制；命中本节"顺序优先"时，本条的"**在一条消息里同时发起**"不适用，改为按序逐个派发（波次规则不受影响）
- [ ] 用 `todo_write` 登记阶段与子任务进度；后台任务 id 与子代理 id 一并记录在案
- [ ] 若有操作因权限不足无法由子代理完成：先向用户上报**具体受限操作**并申请提权，并说明是申请扩大该子代理权限、还是按 §1 的例外由 CTO 代做，**不得静默降级交付**；用户拒绝或本会话禁止提权时，该实施单元进入**终止态**：停止该单元的后续派工，把它排除出评审基数与修复范围，在最终答复中列为"因权限受限未实施"并说明原因，**不得**以省略该项、放宽验收标准或声称已完成来收尾；该单元已落地的部分改动须单独列明并纳入评审
- [ ] **CTO 上下文预算**：CTO 上下文不足以保障「实施 → 评审 → 修复 → 复验」全链验收时，**禁止**派实施类单元；只允许规格 / 评审类可恢复单元（产出落盘即安全）或直接写台账交接并停止派工；用户推进指令不解除本约束——须向用户说明预算缺口并由其裁决。
- [ ] **批次开工指纹**：每批开工（§8 模式下为每个模块波次开工）先记录 `git rev-parse HEAD` 与 `git status --porcelain` 指纹并与台账 / 预期比对；不一致即先走「外来改动处置决策」——中止开工 / 保护性快照提交 / 隔离 worktree 三选一，保护性提交必须在提交信息与台账注明「内容未经本批评审」；非 git 目标按 `§8.4` 替代基线口径取证。处置结论记台账后方可派工。

### 阶段 2 — 实施

- [ ] 子代理并行实施；CTO 期间只做只读核对、准备验收清单，**不重复子代理的工作**

### 阶段 3 — 深度评审（1 实施单元 : 1 评审）

- [ ] 评审总数 = **实施单元个数**（一个单元由多名高级软件工程师共同实施也仍只计 1 个单元、配 1 名评审；§8.2 的相邻小模块合派只合并**承载人数**，N 个模块仍出 N 份评审结论，**结论份数比**不变）
- [ ] **资深评审工程师**必须**未参与**该单元的实施
- [ ] 必须读**实际 diff 与文件原文**，不接受**高级软件工程师**的摘要作为依据
- [ ] 必须主动构造反例、边界、回归与失败路径；能跑就跑（只读边界：不得修改受版本控制文件、不得改变既有行为；写缓存/产物后须清理）
- [ ] 必须检查**安全问题**、**并发与资源问题**、**无关改动**、**风格与依赖违规**
- [ ] 输出：分级（严重 / 中等 / 轻微）+ `文件:行号` + 复现命令与输出 + 明确"通过 / 不通过"
- [ ] **评审结论必须能被 CTO 独立复核，禁止含糊表述**；避免"大家都扫一眼"的走过场式评审

### 阶段 4 — 修复与复验

- [ ] **缺陷修复工程师**必须**未参与**该实施单元的实施（`§8` 全项目深度 Review 模式下另须**未参与评审**，见 `§8.6`）；**独立复验工程师**必须**未参与**该单元的实施与修复，且同样**只读**；确无独立子代理可用时，须在最终答复中**注明本次修复/复验不满足独立性并说明替代措施**；该情形下复验产物必须标注 `NON-INDEPENDENT`；限制解除后须补派一名独立复验工程师做抽查并留档，抽查结论并入最终答复。**严重级别问题必须由独立复验工程师复验通过**
- [ ] 复验只针对**修复点 + 邻接条文**做定向验证，不做全量重审
- [ ] 每轮修复后做**反向还原校验**：由**缺陷修复工程师**在**未跟踪的临时副本**中把补丁逆向还原，哈希必须等于上一轮基线（证明没有附带改动）；校验后必须重新应用补丁并复核最终状态的哈希与内容（**资深评审工程师 / 独立复验工程师不得**就地执行该还原）
- [ ] 循环终止规则见 §3

## 3. 收敛规则（防止无限细化）

0. **分级锚点**（据此判定，不得随意升降级）：导致功能错误、数据损坏、安全问题或回归风险 = **严重**；可复现的行为缺陷、或违反本 skill 任一强制条款 = **中等**；措辞、注释、风格、完备性建议 = **轻微**。**对外可见产物中的错误断言**（引错原文 / 行号 / 提交，复现命令无法只读重放，虚假引用，未验证却写成已验证）= **严重**；**对外可见产物中的越权表述**（承诺合并 / 修复、臆测他人动机、未授权扩大范围）= **中等**。同一事实同时命中多条锚点时，**一律按最高级别判定（从重）**，不得取低。
0.1 **契约基准**（「代码 vs 文档」冲突的取证顺序与归属判定；分级仍按第 0 条）：当「代码」与「文档 / 规格」冲突时，必须先在报告里给出**契约基准判定**小节，回答「以谁为准、依据是什么」，再按下列三条判定归属：
   - 若代码侧有**明确决策记录**（KDoc / 注释 / ADR / 提交信息）声明以**服务端线上报文形态（wire 形态）** / **实测**为准（= 以**实际网络报文**为准，而非文档声明形态）→ 该冲突按「**文档未同步**」计**中等**，**不得**计严重；
   - 若代码侧无任何依据、且按文档实现会出错 → 计**严重**；
   - 判为「文档未同步」时，修复方向是**改文档**，**不得**为此改正确的代码。
1. 只有**严重**与**中等**级问题进入下一轮修复；**轻微**项**累计后一次性收口**（由**缺陷修复工程师**在其后某一轮修复中一并处理），不为它们单独开一轮。（**对外可见产物**的整改仍按 `§9.4` 由**原撰写者**完成）
2. 若某轮复验的新发现**全部为轻微**且无严重/中等项 → 判定**可交付（即"通过"）并停止**。
3. 严重/中等项反复无法修复时 → 如实报告无法解决的原因并停止，不得降级措辞或声称已完成。
3.1 **复验回路与轮次口径**：独立复验（见 §2 阶段 4）发现的**新**问题，按其分级进入**下一轮修复**并计入**新一轮**（分级按第 0 条、契约归属按第 0.1 条）；每轮修复后仍须做**反向还原校验**与**定向复验**（协议均见 §2 阶段 4）；终止条件同第 1、2 条（仅轻微 → 可交付并停止）。
4. **独立复验工程师**不得为凑数升级严重程度，也不得为提前收敛而降级；任何分级都必须给出证据。

## 6. 汇报契约（对用户的最终答复）

1. 目标与最终状态
2. 编排摘要：派工台账机械生成的**子代理清单表**——逐行列 agent id / 角色 / 波次 / 交付物路径 / 状态（返回 / 重派 / 终止态 / 孤儿）；计数 = 表行数，凭记忆写数即自查返工
3. 评审结论与修复情况（含未修复项及原因）
4. 验证证据：实际执行的命令与关键输出
5. 遗留风险与未验证项（如实列出，不得淡化）

（以下第 6–9 项在 §8 全项目深度 Review 模式批次中为强制项；常规批次按 1–5 项汇报，第 10 项对任一批次均为强制项；§9 审查批次模式按 `§9.6` 汇报。）

6. **覆盖表与覆盖率**：模块 → 文件数 → 评审结论（含 `TOTAL` / `COVERED` / `UNCOVERED` 与对账命令的原始输出）；`COVERED` 必须由 `§8.5` 的**逐文件结论行**计数得出，并给出**全部**结论行文件（**每个模块一份**）的绝对路径、条数与 SHA256，`COVERED` 按**仓库相对路径去重后**计数（恒有 `COVERED ≤ TOTAL`，同一文件被两个模块各记一行不得重复计数）；**未覆盖清单**必须显式列出，无则写"无"（清单非空时不得给出"可上生产"）。
7. **问题分级分布计数**（严重 / 中等 / 轻微）与**修复与重构清单**、未修复项及原因（分级机读计数以 `§8.5` 的 `meta` 块为准）；若发生候选实现择优，还须给出候选数、逐维度结论、胜出者，以及隔离落盘与清理的证据。
8. **本批新增的检查点提交清单**（SHA + 提交信息 + 所属模块）。
9. **生产就绪结论**：明确写出"可上生产"或"不可上生产"，并对照 §8.6 的门槛逐条给出依据；不得用"基本可用"之类的措辞替代结论。
10. **批次可中断性（进度台账）**：批次任一时刻必须存在一份**只依赖磁盘**的进度台账（**必须**落盘**在仓库外**，绝对路径写进最终答复；**不得**只存在于上下文），至少含：① 已完成的实施单元 / 模块清单；② 每份交付物的绝对路径 + SHA256；③ 未派工清单（模块名 → 文件数）；④ 下一步动作与已知风险。用户要求暂停 / 长时中断后恢复时，恢复的第一动作是**读该台账**（命令与原始输出记入最终答复）。

**全角色报告落盘**：批次开工时 CTO 在台账声明本批报告归档目录（仓库外路径或 `docs/reviews/` 类），任务书写明绝对路径；**全部角色**（含实施 / 修复 / 重构 / 检查点提交 / 发布执行）的报告一律落盘，回传内容按 §5 回传契约执行；§5 未覆盖的角色只放 `meta` 计数 + 交付物路径 + SHA256 + 未解决项一行。实施 / 修复类报告同样以 `meta` 机读块开头，字段固定为 `unit` / `verdict` / `files` / `sha256_before` / `sha256_after` / `reverse_restore` / `unresolved` 七行、顺序固定；`verdict` 取值域 `pass | fail`，`reverse_restore` 取值 `pass | fail | na`。

**实施 / 修复报告 `meta` 机读口径（与 `scripts/cto_verify.py --kind impl` 的校验逐条对应；本句是值域的唯一权威全文，§4 / §8.9 模板只作指针）**：`files` 取两种形态之一——单文件单元写 ASCII 非负整数 `1`；多文件单元写以 `;` 或 `；` 分隔的仓库相对路径列表（不得含空元素、空白、反引号与 `|`）；`sha256_before` / `sha256_after` 对应取单值（64 位十六进制）或与 `files` 列表等长的 `路径=哈希` 列表（按最后一个 `=` 切分，路径须与 `files` 同位元素一致）；`sha256_before` 的元素或整值可取 `none`（新建文件无基线，此时 `reverse_restore` 必须为 `na`），`sha256_after` 不得取 `none`；before 与 after 对应位全部相等时必须在正文写出 `sha256 相同` 及理由（检索范围为正文：`meta` 机读块不算正文、块内该标记不计入豁免，正文内其它围栏块计入），否则判不通过；`reverse_restore: fail` 时 `verdict` 不得为 `pass`；`unresolved` 写 `无` 或以 `;` / `；` 分隔的未决项简述，其非 `无` 不阻断 `verdict: pass`（未决项仍须逐项落盘正文）。

**证据产物归档**：评审 / 复验 / 验证报告、结论行文件、构建日志、指纹与快照等证据产物一律落盘到本批声明的归档路径（仓库外固定目录，或入库时 `docs/reviews/` 类路径），进度台账逐份登记绝对路径 + SHA256；未登记路径的产物视为未交付（按静默失败 ① 处理）。

**CTO 亲自执行命令自查清单**：最终答复必须逐条列出本批 CTO 亲自执行的每条 mutating / 构建 / 测试 / 提交类命令及其援引的例外条款；无则写「无」。该清单是 §1 例外条款的自查证据，不得省略。

**验收前置校验与重派**：CTO 必须在验收任何一份子代理报告之前，做存在性 + 必需段落校验，并在最终答复中给出所用命令与原始输出。

- **静默失败**的定义（五者任一即成立）：① 子代理返回但约定的交付物**不存在**；② 交付物为 **0 字节**；③ 交付物**缺少必需段落**；④ 已派出但超过任务书标注的启动容忍窗（默认 **30 分钟**）仍零节点、零磁盘副作用（never-started 僵尸）；⑤ 已启动但进度信号中断超过任务书标注的停滞窗（默认 **60 分钟**，或连续两次进度间隔无更新）。④⑤ 的核查动作：先查进度文件与磁盘副作用，再查进程 / 探活；宣告僵尸须把 id 与核查证据记入台账并移出并发计数。**必需段落**按该报告所属模板穷举确定（只此三组，不得增补、不得减少）：ⓐ 评审 / 复验报告（§5、§8.8）= 报告开头的 `meta` 块 + 总体结论（通过 / 不通过 + 理由），其中 §8 的模块评审报告**另须** `conclusions` 块（见 §8.5）；ⓑ 实施报告（§4、§8.9）= `meta` 机读块 + 实测值（字节数 / 行数 / SHA256）+ 反向还原校验结果 + 未解决 / 不确定项；ⓒ 检查点提交回执（§8.4）= 提交 SHA + 提交信息 + 所属模块。
- **重派**：① 子代理失败、超时或被中断（未返回）与 ② 已返回但命中静默失败，两类都**必须**如实说明并**重派**，不得默默略过。**重派上限**：同一实施单元因静默失败**最多重派 1 次**；重派后仍命中静默失败，该单元记入**终止态**（停止该单元的后续派工、排除出评审基数与修复范围），并在最终答复中列为「**因静默失败未完成**」并说明原因，**不得**静默略过；未返回类重派不占该上限，照旧执行并如实说明。
- **增量落盘纪律**：子代理必须先写骨架报告（`meta` 块 + 章节占位）再干活，随后边做边落盘到任务书指定路径（`wip`）；实施类单元分小段编辑、高频落盘，保证死亡现场可交接。
- **重派工作区对账**：重派实施类单元时任务书必须含对账条款——动手前先 `git status` 与 `git diff <基线>` 取证，逐文件声明「继承」或「回滚」；声明继承的半成品改动须在报告「非我产出」清单中逐条列出。
- **中断与收尾处置**：用户中断 / 取消后，CTO 必须先核实全部在途子代理实际生死（取消 ≠ 终止——被转后台者仍可完成并写副作用），核实命令与结果记台账后方可继续；批次收尾时对未返回子代理显式处置（终止，或登记为孤儿：id + 预期副作用清单入台账并在最终答复列出）。

## 7. 反模式

- ❌ CTO 自己动手改一行"省得派子代理"
- ❌ 把同一文件的多处改动拆成多个并行单元（必然冲突）
- ❌ 用高级软件工程师自己的摘要替代资深评审工程师的原文核对
- ❌ 跳过评审阶段直接交付；把未验证说成已验证
- ❌ 让复验无限追轻微措辞（真实教训：一个单文件任务曾因措辞细化跑了 3 轮修复）
- ❌ 在子代理任务书里省略验收标准
- ❌ 同一段引文在两份任务书里各手抄一遍（多单元共享的引文必须来自**单一规格源**，逐字节取用）
- ❌ 规格文件由 CTO 亲自执笔、只派出 1 名规格工程师、或把未被选中的候选规格当规格源引用（规格文件必须由 **2 名规格工程师**独立产出候选，再由 CTO 依据可判定维度择优选定**唯一规格源**）
- ❌ 把"纯协议文档批次可跳过规格层"当成可绕过评审阶段的理由（跳过的是**规格层**，阶段 3 评审与阶段 4 复验照常执行）；其数量仍按**实施单元数**计
- ❌ 只 review "改动过的文件"或只看 `git diff`，就宣称 review 了整个项目（覆盖必须以受版本控制文件全集的 `git ls-files` 对账为准）
- ❌ 以"能跑"代替优雅度审查；或用没有 `文件:行号`、没有证据的泛泛评论充当发现项
- ❌ 重构不提供行为不变的证据（无测试、无等价性校验、无前后行为对比）
- ❌ 同时运行的子代理数超过上限；或因上限**合并、串行化、丢弃**彼此独立的单元
- ❌ 工作区有未提交改动就直接开始某模块的评审或修复（未先打检查点提交）
- ❌ 把多个候选实现**拼凑**成一份，或引用未被选中的候选实现
- ❌ 模块清单只写目录或 glob、不落到文件绝对路径；或覆盖率没有实测对账依据
- ❌ 用 `git add -A` / `git commit --amend` / `--force` 完成检查点提交
- ❌ 用户要求"依次 / 逐个"却并行派工；或把存在共享可变外部状态（同一 PR 评论线程、同一 issue、同一配额 / 速率）的单元拆开并行
- ❌ 两名工程师评审**同一对象集合**（重叠），或按"审查维度"把同一对象拆给多人各看一半，或拆成互不可见的子评审而无人汇总
- ❌ 把 review message / 评论 / issue 草稿当作"顺手写的东西"：不落盘、不留 SHA256、不做独立核对
- ❌ 产物的撰写者自己核对、自己发布；或未核对通过就发布对外内容
- ❌ 对外产物发布后被静默改写（无新版本、无重新核对）
- ❌ 审查批次不给"逐对象结论行"，用"整体都看过了"代替对象级结论

## 8. 全项目深度 Review 模式（叠加层）

> 进入条件：用户要求 review / 审计**整个项目**、要求**覆盖全部代码**、要求分模块深度 review、要求审查业务逻辑与架构，或要求判定"可以直接上生产"。本节是**叠加层**：阶段 1–4、§3 收敛规则、§6 汇报契约、§7 反模式**全部继续适用**，本节只在其上追加模块规格、覆盖对账、逐模块检查点提交、Review 专用模板与生产就绪门槛。

### 8.1 定位：叠加，不新增编号阶段

- **不进入**的情形：只读问答与咨询；只审查指定的 diff、指定文件或指定目录（那走常规批次）；用户明确要求"只改这一处"。
- **与阶段 1–4 的关系**：**不替换、不新增编号阶段**（既有已有"阶段 0 — 快速通道"，再插编号会冲突）。本模式在阶段 1 之前追加两个**前置动作**（按名称称呼，不给编号）：前置动作"**模块规格**"（见 8.2，在派工之前产出并择优唯一规格源）与前置动作"**覆盖基线**"（见 8.3，生成受版本控制文件基线清单并与模块清单双向对账）。之后按模块循环执行阶段 1 → 2 → 3 → 4（见 8.4）。
- **单元划分**：本模式下**一个模块至少是一个实施单元**；模块内部若存在多组可独立验证的改动，按 `§2 阶段 1` 的口径继续拆成多个实施单元（阶段 3 的"1 实施单元 : 1 评审"不变）。评审承载的例外（相邻小模块合派）见 §8.2。

### 8.2 模块规格（模块划分）

> 本节即 `§8.1` 所列的前置动作「**模块规格**」：在派工之前产出，并择优唯一规格源。

- **划分依据（同时满足）**：**架构分层**（入口与接口层、领域与业务逻辑层、数据与持久化层、集成与外部依赖、构建与 CI、辅助脚本与文档）与**业务逻辑**（每个业务能力或用例为一个模块）。
- **每个模块必须给出（缺一不可）**：
  1. **模块名**：稳定标识（小写短横线，例如 `mod-order-lifecycle`），同一批评审内不得改名；
  2. **职责**：1–3 句，说明该模块对系统承担什么；
  3. **涉及文件的绝对路径全集**：逐条列出。**禁止**只写目录或 glob 模式代替文件清单；
  4. **可执行的验证手段**：该模块可跑的构建 / 测试 / lint / 静态检查命令（能跑就跑，跑不了要写明原因）；
  5. **依赖与边界**：与其它模块的接口契约（谁调用谁、数据如何流动）。
  6. **评审深度分级（A / B / C）**：每个模块**必须**标注评审深度，取值只能是下列三者之一——
     - **A 深度**：业务主链（如播放 / 下载 / 同步 / 网络 / 鉴权）——逐文件全文通读 + 对抗性失败路径构造 + 实际跑该模块定向测试 + 契约漂移逐条判定；
     - **B 标准**：逐文件通读 + 关键路径抽查 + 编译 / 定向测试（可用 SKIP-env 跳过并说明原因，例外口径见 §5 构建证据契约）；
     - **C 形式**：仅二进制 / 生成物 / 证据资产——只做存在性、一致性、引用完整性、命名与分组、重复与体积、敏感信息检查，且**必须明确标注"未逐行审查"**。

     级别只改变审查手法、不减少结论集：**逐文件结论行与 `meta` 块无论级别一律必需**。
- **辅助模块**：配置、构建与 CI、脚本、文档、锁文件与二进制资源一律归入"辅助模块：配置 / 脚本 / 文档"，**同样**逐条列出文件绝对路径全集。其中无法逐行审查的文件（压缩产物、锁文件、二进制）必须显式标注"仅做形式审查（存在性、一致性、引用完整性），未逐行审查"，**不得**含糊写成"已审查"。
- [ ] **相邻小模块可合派（不减少结论集）**：当**两个及以上模块同时满足**下列三项——合计文件数 ≤ 8、无共享文件、相互无编译期依赖——**可由同一名评审工程师在同一任务书内并行承担**。合派只合并**派工主体**：
  - ① 仍须为**每个模块**分别出具 `meta` 块与 `conclusions` 块（结论集不变：N 个模块 = N 份 `meta` 块 + N 份 `conclusions` 块）；
  - ② 报告须按模块分节，且**不得**跨模块合并发现项计数；
  - ③ `§2 阶段 1` 的「评审总数 = 实施单元个数」与 `§2 阶段 3` 的「1 实施单元 : 1 评审」均按**计数比**成立——合派不合并、不串行化、不丢弃任何单元，改变的只是**承载人数**（1 名评审工程师承载 N 份评审结论）；合派后的并发计数仍按 `§2 阶段 1` 的并发上限口径（含全部角色）。
- **本清单是一份规格**：必须落盘为文件（给出绝对路径），并**按 `§2 阶段 1` 的"规格文件产出"执行**——2 名规格工程师并行、各自独立产出完整候选（互不可见、互不参考），CTO 依据可判定维度择优选定**唯一规格源**，其余候选作废且不得被任何任务书引用。所有模块评审任务书必须从该规格源**逐字节取用**模块名与文件全集。

### 8.3 覆盖保证（可独立验证）

- **基线清单**（命令与原始输出必须留档）：

  ```text
  git ls-files
  git ls-files --others --exclude-standard
  ```

  第一条给出**受版本控制文件全集**（覆盖率的分母）；第二条给出"未跟踪但未被忽略"的文件，必须显式列出并说明处置（归入某模块，或列入未覆盖清单）。两条命令的输出均须记录**条数**与**清单文件的 SHA256**。
- **覆盖表**（最终答复强制项，逐模块一行）：

  | 模块 | 职责 | 文件数 | 评审结论 | 发现项（严重 / 中等 / 轻微） | 修复或重构状态 |
  |---|---|---|---|---|---|

  文件**绝对路径全集**落在模块规格文件里，不塞进最终答复；覆盖表只给汇总。
- **对账方法（双向差集，可判定）**：把模块规格中所有文件路径转换为仓库相对路径并去重，得到集合 M；`git ls-files` 给出集合 T。两个方向都必须为空：
  - `T - M` 为空：**没有**受版本控制文件落在任何模块之外（漏报即**不通过**）；
  - `M - T` 为空：模块清单里没有不存在的文件（多报即**不通过**）。

  参考实现（在仓库根执行；Windows PowerShell 5.1 与 PowerShell 7 均可运行）：

  ```powershell
  # 路径 A（推荐，可直接执行）：从"模块文件清单"读取路径集合 M。
  # 清单是模块规格中"涉及文件的绝对路径全集"一节的可机读副本：每行一个路径
  # （绝对路径或仓库相对路径均可），以 # 起始的行为注释，编码 UTF-8 无 BOM。
  $Manifest = 'C:\path\to\module-files.txt'   # 唯一需要人工填写的值：清单文件的绝对路径
  # $T 必须带 -c core.quotePath=false：默认 core.quotePath=true 会把非 ASCII 路径输出成
  # 八进制转义（实测 "src/中文文件.py" 变成 "src/\344\270\255\346\226\207..."），与清单里的
  # 真实路径对不上，会造出**虚假的"不通过"**。
  $T = git -c core.quotePath=false ls-files | Sort-Object -Unique

  # 第一步：存在性校验必须与集合比较**分开**做，且**不得**依赖 Resolve-Path 的静默丢弃行为。
  # Resolve-Path 对不存在的路径只写非终止错误、不产出对象；把它嵌在管道里再调 ToString()
  # 会让该条目**静默消失**（实测：清单里的 ghost 路径既不出现在 $M 里、也不出现在
  # Compare-Object 的输出里），于是"清单里有不存在的文件"永远报不出来，直接导向假通过。
  # 下面改用 Test-Path 逐条显式判定：$Missing 非空即判"不通过"。
  $Missing = @()
  $Exists  = @()
  foreach ($ManifestLine in Get-Content -LiteralPath $Manifest -Encoding UTF8) {
      $p = $ManifestLine.Trim()
      if ($p -eq '' -or $p.StartsWith('#')) { continue }
      if (Test-Path -LiteralPath $p -PathType Leaf) { $Exists += $p } else { $Missing += $p }
  }
  # 判定 ①：清单中存在性校验失败的条目；非空即"不通过"（本判定**不**依赖任何静默丢弃行为）。
  if ($Missing.Count -gt 0) { "存在性校验不通过（清单里有不存在的文件）："; $Missing }

  # 第二步：只对**已确认存在**的条目做归一化（绝对路径 → 仓库相对路径，统一 '/' 分隔）。
  # $Root 与 $full **必须走同一套归一化，且该口径必须能展开 8.3 短路径**：实测
  # Resolve-Path 会**原样保留**短形式（"C:/Users/LAEVAT~1/..."），只有 Get-Item 的
  # FullName 会把它展开成长形式。两侧口径不一致时，清单用短路径会造出每行一对
  # "=>" 与 "<=" 的**虚假"不通过"**。
  $Root = (Get-Item -LiteralPath (Get-Location).ProviderPath).FullName
  $M = @($Exists | ForEach-Object {
           $full = (Get-Item -LiteralPath $_).FullName
           if ($full.StartsWith($Root, [StringComparison]::OrdinalIgnoreCase)) { $full.Substring($Root.Length) }
           else { $full }
       } | ForEach-Object { $_.TrimStart('\', '/') -replace '\\', '/' } | Sort-Object -Unique)

  # 判定 ②/③：Compare-Object 必须无输出。
  #   '=>'（M - T）非空 = 清单里有、而受版本控制文件全集里没有的条目：包含"存在但未被跟踪"
  #        的文件，也包含越出仓库的路径 → **不通过**；
  #   '<='（T - M）非空 = 有受版本控制文件落在任何模块之外（漏报）→ **不通过**。
  # 判定 ①/②/③ 必须**同时**为空，才算覆盖通过。
  Compare-Object $T $M        # 必须无输出；有任何输出即覆盖不通过
  ```

  路径 B（无清单文件时）：路径集合只能由人手工构造，因此**只作为注释占位**，
  **禁止**直接粘贴执行（`<...>` 会被 PowerShell 当作重定向而报错）：

  ```text
  # $M = <模块规格中全部文件路径转为仓库相对路径> | Sort-Object -Unique
  ```

  只要 `Compare-Object` 有任何输出，覆盖即为**不通过**，必须回到 8.2 重划模块。

- **上述三条命令各证明什么、不证明什么**（不得拿命令当护身符）：
  - `git ls-files`：证明**受版本控制文件全集**（分母 `TOTAL` 的来源），并对账 `T - M` 为空（无漏报）；**不证明**这些文件被真正评审过，也**不覆盖**被忽略文件；子模块整体按下方"**子模块 / gitlink**"保守规则处理；
  - `git ls-files --others --exclude-standard`：证明**未跟踪且未被忽略**的文件已被显式处置（归入某模块或列入未覆盖清单）；**不证明**被忽略文件的处置是否合理（这由下一条"分母自查"负责）；
  - `Compare-Object $T $M`：证明模块清单与受版本控制文件全集在**集合层面互相无缺无余**；**不证明** `COVERED`——它无输出只说明 `M` 与 `T` 相等，与"每个文件是否被逐文件给出结论"无关，二者必须分别取证。
- **记数（口径必须可判定，禁止用"分母做小"造出满分）**：`覆盖率 = COVERED / TOTAL`。
  - `TOTAL` = **本仓库** `git ls-files` 的条数（受版本控制文件全集；gitlink 路径本身计 1 条，子模块内部文件**不计入**，见下"子模块 / gitlink"）；
  - `UNCOVERED = TOTAL - COVERED`；
  - `COVERED` = **已实际评审**的文件数——即该文件在 `§8.5` 的模块评审中**至少有一条明确结论**：要么在发现项表中被点名（发现 N 项），要么被逐文件结论行显式写为"无问题"。**只被模块清单列出不算 `COVERED`**；被列出但未逐文件给结论的文件一律计入 `UNCOVERED`；**计数按仓库相对路径去重**——同一文件被两个模块各记一行时**只计一次**，因此恒有 `COVERED ≤ TOTAL`；
  - **`COVERED` 不得由模块清单推算**，必须由 `§8.5` 要求的**逐文件结论行**计数得出；最终答复须列出**全部**结论行文件的绝对路径、**条数**与 SHA256——**每个模块一份**结论行文件，并按**仓库相对路径去重后**计数 `COVERED`（同一文件被两个模块各记一行**只计一次**，保证不变式 `COVERED ≤ TOTAL`），供 CTO 与独立复验工程师随机抽取若干条回读原文核对；
  - 因此 `COVERED` 与 `TOTAL` **不恒等**：只要有一个文件没有逐文件结论行，`UNCOVERED > 0`，覆盖率即小于 100%。三项数值与对账命令的原始输出一并记入最终答复。
- **未覆盖清单**：必须显式给出（无则写"无"）。**禁止**省略该小节，也**禁止**用"其余文件影响不大"之类的措辞替代清单。该清单**非空**时，按 `§8.6` 门槛 6 **不得**给出"可上生产"结论。
- **覆盖自证**：每个模块的评审任务书都必须要求**资深评审工程师**提交"本模块文件全集 + 对账命令与原始输出"；最终轮由**独立复验工程师**重跑对账命令，验证覆盖率数字与清单一致。
- **分母自查（忽略规则必须公开，防止把分母做小）**：不得把被忽略的文件直接计入分母，但**忽略规则本身必须被审查**：
  1. **列出全部生效的忽略来源**：仓库根与各嵌套目录的 `.gitignore`、`.git/info/exclude`、以及全局 `core.excludesFile`（`git config --get core.excludesFile`；**未设置时该命令退出码为 1**，须据此如实记录"未设置"）；对具体路径可逐条取证：`git check-ignore -v --no-index <路径>`（**退出码 0 = 被忽略**并打印命中规则所在文件与行号，**退出码 1 = 未被忽略**）；
  2. **逐条列出被排除内容与理由**：若上述忽略规则排除了**任何目录或源码文件**，必须逐条列出被排除的路径与理由；取证命令：`git ls-files --others --ignored --exclude-standard`（列出全部被忽略的未跟踪文件，**精确到文件**）与 `git status --ignored --porcelain`（`!!` 前缀即忽略项；输出为**混合粒度**——整目录被完全忽略时**聚合为该目录一行**，否则**逐文件**列出，实测 `!! alldir/` 与 `!! mixdir/b.log` 并存，故**不得**假定它总是按目录聚合）；
  3. **抽查（由资深评审工程师执行）**：对被忽略路径下的**真实文件数**计数并与忽略清单条数比对，二者不一致必须解释——`Get-ChildItem -LiteralPath <被忽略目录> -Recurse -File -Force | Measure-Object | Select-Object -ExpandProperty Count`；
  4. **被忽略的源码文件必须落账（"不计入"须有可判定护栏）**：凡被忽略且落在**源码白名单**内者——扩展名 `*.py|*.ts|*.tsx|*.js|*.jsx|*.go|*.rs|*.java|*.c|*.cc|*.cpp|*.h|*.hpp|*.cs|*.rb|*.php|*.kt|*.swift`，或路径落在 `src/`、`core/`、`lib/`、`app/`——**一律强制计入未覆盖清单**；"不计入"**仅在**能出示该路径的 **vendored 上游出处（URL + 版本 / commit）** 或**可独立复核的生成物 / 测试夹具证据**时成立。非构建产物、非依赖目录、非缓存的**源码文件**必须计入**未覆盖清单**，或给出"不计入"的**明确理由**（例如第三方 vendored 代码、生成物、测试夹具），理由必须可被独立复核；
  5. **稀疏检出**（sparse-checkout）导致的"已登记但未检出"文件必须显式说明，并计入未覆盖清单。取证方法：`git ls-files -t` 中带 **`S `** 前缀（skip-worktree）的条目即"已登记但未检出"，`git sparse-checkout list` 给出生效的模式集合，`git config --get core.sparseCheckout` 给出开关状态；命中者**必须**逐条计入未覆盖清单（实测：稀疏检出后 `git ls-files` 仍列出未检出的文件，只有 `git ls-files -t` 能把它们与真正检出的文件区分开）。
- **子模块 / gitlink（保守规则：不展开、不对账、直接失败关闭）**：
  1. **检测（唯一权威判据）**：`git -c core.quotePath=false ls-files -s | Select-String -Pattern '^160000'` **无命中**才是"无子模块"（此时本节整条不适用）；命中行的末列即子模块路径（行格式 `<mode> <object> <stage>\t<path>`）。**不得**用 `.gitmodules` 是否存在作判据：未注册的 gitlink（有 `160000` 条目、无 `.gitmodules`）真实存在，而 `Test-Path .gitmodules` 与 `git config --file .gitmodules --get-regexp '^submodule\..*\.path$'` 此时都会给出"无子模块"的**肯定性错误结论**（实测：前者返回 `False`，后者退出码 1 且输出为空）。
  2. **存在即失败关闭**：只要存在**任一** `160000` 条目——不论是否已注册、是否已 `git submodule update --init --recursive` ——该子模块**连同其嵌套子模块与全部内部文件**整体计入**未覆盖清单**，逐条列出 gitlink 路径并注明"**需用户裁决或另行独立评审**"；据此 `§8.6` 门槛 6 不满足，本模式**不得**给出"可上生产"，只能给"**不可上生产 / 未完成**"。**禁止**把子模块当作不存在，也**禁止**用任何形式的子模块展开对账去反推覆盖率或据此翻案。
  3. **分母口径（消除双重口径）**：`TOTAL` 恒为**本仓库** `git ls-files` 的条数——gitlink 路径本身计 1 条，其内部文件**不计入**；双向差集对账**只在超级仓库范围内**成立。存在 gitlink 时，路径 A 对 gitlink 路径本身（工作树上是**目录**）会报"存在性校验不通过"，清单里不写它则会报 `T - M` 的 `<=`——两者都是**本条预期的失败关闭**，**不得**据此删改清单、放宽本节或再叠一套对账机制来"修好"它。
  4. 用户要求把子模块内容纳入本次覆盖时属**规格变更**：由用户裁决覆盖口径（递归范围、分母定义、评审规模）后**另开批次**，以**该子模块自身的仓库根**独立重跑 `§8.3`–`§8.6`，不得与本仓库覆盖表混算。
- **非 git 项目（替代基线）**：先用 `git rev-parse --is-inside-work-tree` 判定（**非仓库时该命令以退出码 128 报 `fatal: not a git repository`**）。若不是仓库，覆盖率**无法**与版本控制对账，必须给出**替代基线**：`Get-ChildItem -LiteralPath <项目根> -Recurse -File -Force` 的输出，扣减显式声明的忽略集（例如 `node_modules`、`bin`、`obj`、构建产物），落成清单文件（给出绝对路径）并记录其 SHA256；同时必须在最终答复中明确写出"**该情形下覆盖率无法与版本控制对账**"。**该情形下禁止给出"可上生产"结论**（`§8.6` 门槛 6 无法满足），只能给出"**未完成**"。

### 8.4 逐模块循环与检查点提交

对每个模块，按下列顺序执行：①**检查点提交**（该模块的评审或修复**开始之前**）→ ②阶段 1 派工 → ③阶段 2 实施（修复 / 重构）→ ④阶段 3 模块深度评审（见 8.5）→ ⑤阶段 4 修复与定向复验 → ⑥覆盖表落账 → 下一个模块。每个模块波次开工同样执行 §2 阶段 1「批次开工指纹」，指纹不一致先处置再进入检查点提交。纯审计批次（无修复对象）变体：上列循环中步骤 ③ 实施与 ⑤ 的修复环节可跳过，定向复验按**批次级**执行（对全部模块评审产物统一复验一次）；检查点、派工、评审、落账环节不变。

**检查点提交规则**：

- **执行者**：检查点提交**必须**由一名**高级软件工程师**执行，**不得**指派给 CTO——CTO 的授权是"只读命令取证、**不改变受版本控制内容与既有行为**"（`§1`），而提交会改变仓库状态；该执行者计入 `§2 阶段 1` 的并发上限。
- **触发**：先运行 `git status --porcelain`。有输出 → 必须提交；无输出 → 记录"无未提交改动"并继续。
- **提交信息约定**：`chore(checkpoint): before review of <模块标识>`；同一模块内多轮修复的中间检查点用 `chore(checkpoint): <模块标识> round <n>`。
- **只提交既有改动**：默认 `git add -u`（只暂存**已跟踪**文件的修改与删除）；本模块相关的**未跟踪新文件**必须**逐个显式** `git add <绝对路径>`。**禁止** `git add -A`、`git add .`、`git add -f`。
- **提交前核对**：执行 `git status` 与 `git diff --cached --stat`；若暂存区出现与本模块无关的文件，用 `git restore --staged <路径>` 撤出后重试（**不得**丢弃工作区改动）。
- **禁止**：`--force`、`--amend`、`rebase`、`reset --hard`、`filter-branch`，以及任何改写历史的操作；禁止修改 remote、仓库**可见性**（public / private）、tag，**绝对禁止删除任何分支**（本禁令适用于本模式**全过程**，不限于检查点子步骤）；唯一例外是按 `§8.7` 作废清理**本批自建**的 `candidate/*` 候选分支——该情形下**必须**删除。`main`、任何**远端分支**与**他人分支**在任何情况下都**不得**删除，**不设**任何例外。
- **不在版本控制下时**：先用 `git rev-parse --is-inside-work-tree` 判定。若不是仓库，**必须先向用户说明并取得明确同意**才能 `git init`，且须一并确认初始提交范围与 `.gitignore`；**不得擅自初始化**。未获同意时该模块进入"**无回退基线**"状态：最终答复必须显式列出，且**不得**在该状态下做重构（只允许只读评审并列出发现项）。
- **无版本控制时的回退基线替代**：若目标文件**不在任何 git 仓库内**（例如 agent 全局 skill / 配置目录），可用**仓库外时间戳备份 + SHA256** 作为回退基线：改动前把文件复制到**目标目录之外**并记录字节数 / 行数 / SHA256，改动后按 `§2 阶段 4` 的反向还原校验协议执行——把备份写回 → 哈希须等于基线 → 再恢复改动后状态 → 哈希须等于改动后。**替代范围（仅此一处）**：本条**仅**替代上条「**无回退基线**」的**判定**，**不解除**上条关于 `git init` **必须取得用户同意**的要求（上条的同意前置条件不变）；上条原有另两项后果——「**不得**在该状态下做重构」与「最终答复**必须显式列出**」——**只有在**替代基线**存在**（给出绝对路径 + 字节数 / 行数 / SHA256）**且**上述反向还原校验**通过**（写回后哈希等于基线、恢复后哈希等于改动后）时才解除；二者缺一（备份不存在 / 校验未执行 / 校验未通过）则上述两项后果**仍然生效**。**备份粒度**：不得粗于实施单元——**每个实施单元动手前各备一份**；**禁止**用批次级单一备份充当多单元的还原基线（对第 N 单元执行「写回 → 比对 → 恢复」时会把第 1…N−1 单元的既有改动一并回滚，直接破坏既有改动）。
- **检查点提交是回退基线**：其 SHA 即该模块后续"反向还原校验"（`§2 阶段 4`）的基线。
- **推送不等于检查点提交**：`git push` 属对外发布（`§9.5`），如需推送须由 CTO 显式授权并由**未参与该模块实施**的高级软件工程师执行；本节的检查点提交仅指本地 `git commit`。
- 最终答复必须列出本批产生的**全部新增提交**（SHA + 提交信息 + 所属模块）。

### 8.5 模块评审维度与发现项格式

每个模块的深度评审（阶段 3 在本模式下的展开）必须**逐维度**给出结论，不得只挑顺手的看：

- **(a) 缺陷**：功能错误；安全（注入、越权、密钥与凭据、依赖漏洞）；并发与资源（竞态、死锁、泄漏、无界增长）；边界与失败路径（空值、越界、超时、重试、部分失败）；数据一致性（事务边界、幂等、迁移可逆）；回归风险。
- **(b) 不优雅实现**：重复代码；耦合过紧；命名不当；圈复杂度与嵌套过深；抽象层次不当（过度设计或过早抽象）；错误处理草率（吞异常、丢失上下文）；死代码与不可达分支；依赖违规（越层引用、循环依赖）；可测试性与可观测性差（不可注入、缺日志与指标）。
- **(c) 架构与业务逻辑**：模块职责是否清晰；有无循环依赖或越层调用；状态管理是否混乱；接口契约是否稳固（参数与返回、错误码、版本兼容）；错误传播路径是否可追踪；硬编码与配置（魔法数、环境差异）；性能与资源热点；业务规则与代码是否一致；事务、幂等与重试边界。

**逐文件结论行（`COVERED` 的唯一取证来源，缺一不可）**：模块评审必须对该模块文件全集的**每一个文件**给出一行结论，结论行的文本格式由本节的 `conclusions` 机读块**唯一规定**（只有两种合法形态，此处不再另立格式；旧写法 `相对路径 | 结论（发现 N 项 / 无问题）` 已作废），其中 `N` 为该文件在发现项表中被点名的条数、也等于该行括号内 id 的个数。结论行必须落盘为文件（给出绝对路径并记录 SHA256），供 CTO 与独立复验工程师**随机抽取若干条回读原文核对**：**每个模块一份**结论行文件，且回读抽样**必须量化**——最低抽样量**分层确定**：结论为"发现 N 项"（`N ≥ 1`）的文件**全查**；结论为"无问题"的文件抽取 `max(10, ⌈N0 × 10%⌉)` 条（`N0` 为"无问题"结论行的条数），并设**回读上限 1000 条**——超出上限时按文件规模与变更热度分层抽样，分层口径必须记录。抽样方式与随机种子、被抽中的条目及其回读结论必须逐条记录，结论行**按仓库相对路径去重后**计数 `COVERED`。**只要抽样中发现任一敷衍或伪造的结论，该模块 `COVERED` 立即归零、该模块必须重审**（按 `§3` 第 0 条，违反本 skill 强制条款 = 中等项）。**未出现在结论行中的文件、或结论含糊（例如"整体看过了"）的文件，一律不计入 `COVERED`。**

**`conclusions` 机读块（格式唯一权威全文；§8.8 任务书模板只作指针）**：结论行**必须**集中在一个独立的围栏代码块（起始行 = 三个反引号 + `conclusions`，围栏必须闭合）内，**一行一条**，格式严格为下列两种之一（**只此两种，不得并存第三套格式**）：

```conclusions
<仓库相对路径> | 发现 <N> 项 (<id1>, <id2>, …)
<仓库相对路径> | 无问题
```

两种形态的判定规则：**形态 A**（`发现 <N> 项`）——`<N>` **必须**同时等于括号内 id 的个数与该文件在发现项表中被点名的条数（两个等式缺一即判**不通过**），括号内只允许写 id，**不得**写行号或摘要；**形态 B**（`无问题`）——该文件在发现项表中**未被点名**（即 `N = 0`），此时**不得**写括号、**不得**写「发现 0 项」。`<id>` 的形态与编号规则见下文「发现项格式」。

该代码块必须**包含文件全集的每一个文件，且仅包含这些文件**；**可机械校验的不变量**：块内结论行的**条数必须等于该模块文件全集的条数**（逐文件一行、无重复、无漏项，重复或漏项均判**不通过**）；**禁止**把结论行只散落在正文表格里，**禁止**把整篇报告塞进「结论行文件」；CTO 侧用本 skill 自带的 `scripts/cto_verify.py --report <报告> --manifest <清单>` 机械核对（退出码 0 = 通过；1 = 契约违规；2 = 用法/IO 错误）——提取条数与模块清单条数必须相等，不相等即判**不通过**。
> 用法：`python scripts/cto_verify.py --help`；批量核对用 `--dir <报告目录> --manifest-dir <清单目录>`。

**`meta` 机读块（格式唯一权威全文；§5 与 §8.8 的模板只作指针）**：报告**开头**必须有一个独立的 `meta` 围栏代码块（其前只允许标题行、注释与空行），字段固定为 `module` / `verdict` / `severe` / `medium` / `minor` 五行、**顺序固定**、值以 `: ` 分隔、计数为非负整数，围栏必须闭合（字面示例如下）：

```meta
module: mod-order-lifecycle
verdict: pass
severe: 0
medium: 2
minor: 5
```

其中 `verdict` 的取值域**只能是** `pass | fail`（`pass` = 本模块总体结论为「通过」，`fail` = 「不通过」），**不得**写「基本通过」「大体通过」等任何其它取值；`severe` / `medium` / `minor` 必须分别等于发现项表中同级行数（自洽），**不得**使用"约""若干""多项"等模糊量词；CTO 与独立复验工程师只读该块，不解析自然语言。

**发现项格式（缺一不可，`id` 置于发现项表首列）**：**`id`** + `文件:行号` + **证据**（可复现的命令与原始输出 / 最小反例 / 原文引用，至少一项，且必须能被他人只读重放）+ **为什么这是缺陷或不优雅**（对照本 skill、项目级规范或公认原则的哪一条）+ **建议修法** + **分级**（按 `§3` 第 0 条的分级锚点判定，不得随意升降级）。**`id` 的编号规则**：形如 `F-01`（`F-` + 两位十进制序号，超过 99 时按实际位数自然扩展），**模块内唯一**，按发现顺序在发现项表中**自上而下从 `F-01` 起连续编号**（不得跳号、不得复用、不得跨模块续编）；`conclusions` 块引用的 id **必须**在本模块发现项表中存在且唯一，出现表中没有的 id 即判**不通过**。

**禁止**：以"能跑"代替优雅度审查；用没有 `文件:行号`、没有证据的泛泛评论（如"这块有点乱""建议优化"）充当发现项。

### 8.6 修复 / 重构与"生产就绪"门槛

- **按问题簇派工**：一个"问题簇" = 同一根因，或同一文件 / 同一逻辑单元内的一组发现项。缺陷修复工程师必须**未参与**该单元的实施与评审。**同一文件的多处改动不得并行**（同 `§2 阶段 1`），必须交给**同一名缺陷修复工程师**串行完成（实施阶段的同文件规则见 `§2 阶段 1`：交给同一名高级软件工程师）。
- **允许重构**，不只是补漏：本节的重构由**缺陷修复工程师**执行（`§1` 角色契约已覆盖该职责），不得改派给该单元的实施者。重构必须**行为不变**，并至少给出下列一项证据：
  1. 既有测试全绿：改动前后的命令与原始输出；
  2. 等价性校验：属性或不变量测试、黄金文件对拍、新旧实现双跑对拍；
  3. 前后行为对比：同一输入的输出 / 接口响应 / 日志字段逐字段一致；差异必须逐条解释并经 CTO 认可。
- **生产就绪门槛**（逐条判定；"可以直接上生产"的结论只有在**全部满足**时才成立）：
  1. **严重与中等**级问题**全部关闭**；若按 `§3` 第 3 条确实无法解决，必须如实报告并给出"**不可上生产**"的结论，不得降级措辞；
  2. 每一项重构都有回归证据（见上）；
  3. 不存在"未验证却说已验证"：所有结论都附实际执行的命令与原始输出；
  4. 性能 / 资源敏感改动有**量化**对比（前后同口径测量）。**"敏感"的触发线**——改动触及下列任一项即必须给出量化对比：① I/O（磁盘 / 文件 / 序列化与反序列化）；② 网络（HTTP、RPC、数据库往返）；③ 热路径或循环（被高频调用、位于请求主链路，或单次调用的复杂度 / 迭代次数发生变化）；④ 数据结构规模（集合、缓存、索引、批处理批大小）；⑤ 并发或异步（线程池、锁、通道、并发度）；⑥ 缓存（新增 / 移除缓存层或有命中率影响）。**同时必须达到实质门槛**（否则判为"不敏感"）：a) 新增 / 修改 / 删除的**净行数 ≥ 30**；或 b) 改动位于**请求主链路 / 循环体 / 并发结构**内；或 c) 改变了**复杂度 / 迭代次数 / 批大小 / 缓存命中路径**。仅重命名、纯格式、注释或纯文本改动，以及净行数 < 30 且不落在上述热路径内者，一律判为**不敏感**。**至少必须报告**：**p50 与 p99 延迟**，以及**峰值内存**或**分配次数 / GC 次数**（二者取其一带上口径）。**必须前后同口径**：同一命令、同一输入规模、同一机器、同一轮次，并给出命令原文与原始输出，注明测量轮数与样本量。若改动经论证**不触及**上述任一项，必须显式写出"不敏感"及其依据，**不得**留空；
  5. 未关闭项（含轻微项）**显式列出**并说明原因与影响面；
  6. 覆盖率按 `§8.3` 达到 **100%**（即 `UNCOVERED = 0`）。**未覆盖清单非空时不得给出"可上生产"**；覆盖率不足 100% 只能表述为"**未完成**"——未覆盖清单仍须按 `§8.3` 逐条列出并给出理由，但**理由不构成通过条件**。
- 修复后必须做**定向复验**：独立复验工程师（**只读**，且未参与该单元的实施与修复）只针对**修复点 + 邻接条文**验证，不做全量重审；**严重**级别问题必须由独立复验工程师复验通过。

### 8.7 候选实现择优在 Review 模式下的应用

- **唯一定义在 `§2 阶段 1` 的"候选实现择优"**：择优维度（七项可判定维度）、三种合法**隔离方式**、未选中候选的**作废规则**、以及候选子代理的**计数口径**，一律以该条为准；本节**只**规定 Review 模式下的特殊要求，不重复上述定义。两处若出现字面出入，以 `§2 阶段 1` 为准；**但角色指派以 `§8.6` / `§8.7` 的例外为准**。
- **触发**：某个模块的修复或重构存在**多条合理实现路径**且优劣不易先验判定时，按 `§2 阶段 1` 的"**候选实现择优**"执行（含候选人数默认值与"互不可见"的独立性要求）。
- **与"规格文件产出"的区别**：后者的产出物是**规格文件**（规格工程师撰写文本），本条产出物是**代码改动**（高级软件工程师写作实现）。两者可在同一批同时发生，**各自独立计数**，并**都计入** `§2 阶段 1` 的并发上限。涉及 `§8.6` 的行为不变重构时，候选实施者与胜出候选落地者一律为**缺陷修复工程师**（`§8.6` 优先于本条对候选角色的一般指称）。
- **Review 模式下的特殊要求（本节唯一实质内容，其余全部指向 `§2 阶段 1`）**：
  1. **候选分支基线**：候选分支一律从本模块**检查点提交**（`§8.4`）的 SHA 建立，**不得**从工作区未提交状态建立；独立工作树的建立命令为 `git worktree add <临时路径> -b candidate/<模块标识>/<n> <检查点SHA>`——**必须显式给出检查点提交的 SHA**，省略该参数时 `git worktree add -b` 会**静默**从当前 `HEAD` 建立分支；建立后**必须**在新工作树内执行 `git rev-parse HEAD` 校验其等于 `<检查点SHA>`，输出留档；（本工作树由该候选的实施者建立，`§2 阶段 1` / `§8.6`）
  2. **候选分支上的禁令照旧**：在候选分支上**禁止** `--force`，**禁止**任何改写历史的操作（`§8.4` 的全局禁令在候选分支上同样生效）；
  3. **清理执行者**：候选作废时的 `git worktree remove` 与候选分支删除**必须**由一名**高级软件工程师**执行，**不得**指派给 CTO（`§1`：CTO 只读、不改变受版本控制内容与既有行为）；该执行者计入 `§2 阶段 1` 的并发上限；
  4. **清理必须两步，缺一即视为未清理**：`git worktree remove` **不会**删除分支（实测：移除工作树后 `candidate/<模块标识>/<n>` 仍然存在），因此工作树移除后**必须**再执行 `git branch -D candidate/<模块标识>/<n>`；候选分支未被合并，`git branch -d` 会以"未完全合并"拒绝（退出码 1），故用 `-D`——它只删除候选分支引用，**不属于** `§8.4` 禁止的改写历史类操作；
  5. **清理证据**：`git branch --list 'candidate/*'` 与 `git worktree list` 的原始输出必须留档（前者应无输出），作为"候选已作废"的证据；
  6. **落地与复验**：**胜出候选**落到目标文件后，除 `§2 阶段 1` 要求的验收标准与反向还原校验外，还须报告实测值（字节数 / 行数 / SHA256，改动前与改动后），并重跑该模块 `§8.5` 的逐维度评审与**逐文件结论行**；
  7. **落账**：择优事实与理由、候选数、逐维度结论、胜出者、落盘位置与清理证据记入最终答复（`§6` 第 7 项）。

## 9. 审查批次模式（叠加层 · 对多个外部对象做 review / 审计）

> 进入条件：用户要求 review / 审计**多个外部对象**（多个 PR、commit、分支、issue、文件集或仓库），或明确要求"依次 / 逐个 / 全部"审查时。本节是**叠加层**：阶段 1–4、§3 收敛规则、§6 汇报契约、§7 反模式全部继续适用；覆盖整个项目时 §8 同时适用。本节只在其上追加**审查单元**口径、**逐对象结论行**、**产物独立验证**与**发布门槛**。

### 9.1 审查单元与计数口径

- **默认：每一个被审对象 = 1 个审查单元**（例如每个 PR 一个单元），审查单元数在**派工时冻结**并记入最终答复。
- **允许合并分组的唯一情形**：对象之间存在**共享可变外部状态**（定义见阶段 1"**顺序优先**"），或对象本身就是同一验收标准的多个片段；分组方案由 CTO 给出并冻结，**不得**由实施者临时决定。合并分组的目的是把共享状态收敛到**单一所有者**下**串行**处理，**不是**为了并发；合并后仍按 `§9.2` 串行执行。
- **禁止**的划分：①两名工程师评审**同一对象集合**（重叠）；②按**审查维度**把同一对象拆给多人（维度是单个评审者的**必查清单**，不是拆分依据）；③把同一对象拆成多个互不可见的子评审且无人汇总。
- 每个审查单元由**唯一负责人**（本模式下即**资深评审工程师**，见 `§9.7`）完成，并产出**逐对象结论行**：`对象标识 | 版本 / 提交 SHA | 结论（通过 / 不通过 / 无法判定）| 发现 N 项（严重 a / 中等 b / 轻微 c）| 结论类型分解（通过 x / 不通过 y / 无法判定 z）| 撰写者 <角色> | 核对者 <角色>`（版本 / 提交 SHA 供 `§9.3` 构造对象键与检测陈旧审查；撰写者与核对者必须是两名不同人员）。
- **计数**：审查批次中审查单元**同时是实施单元**，其审查产物即该单元的实施成果；`§9.4` 的产物独立核对**就是**该单元的阶段 3 评审（同一动作的两面，不重复计数）。
- **与 §8 同时适用时**：§8 的模块单元与 §9 的对象单元**分别计数、各自独立评审**（`§8.1` 一个模块至少一个实施单元；本节一个对象一个审查单元）；同一证据可复用，但**不得**据此合并、省略任一口径的结论行。

### 9.2 顺序（与阶段 1"顺序优先"叠加）

- 用户要求"依次 / 逐个 / 按顺序"时，**严格按用户给定顺序串行**；未指定顺序时按稳定自然顺序（编号升序或提交时间升序）。
- 命中串行情形时，串行粒度 = **审查单元**：一个对象完成"评审 → 产物核对 → 落账"后才派下一个对象；**禁止**为并发把多个对象塞给同一名工程师"一起看"，也**禁止**让第二个对象与前一个对象同时在跑。
- 无显式顺序要求、且对象之间确**无顺序依赖**也**无共享可变外部状态**时，可并行；并发上限与波次派工按阶段 1 执行；命中阶段 1"顺序优先"任一情形（含共享可变外部状态）时一律串行。

### 9.3 覆盖对账（可独立验证）

- CTO 先**只读枚举**被审对象全集 T（例如 `gh pr list --state all --limit 1000 --json number,title,headRefOid`、`git log --format=%H`），记录命令原始输出、条数与 SHA256。**枚举命令必须显式分页或设限**（`gh pr list` 默认只返回 30 条，照抄默认值会把分母做小、造出"假全覆盖"）；T 的条数须与仓库对象计数**独立交叉核对**后才可记为全集。
- **对象键 = `(对象标识, 版本 / 提交 SHA)`**：T 侧使用枚举时的现状 SHA（如 `headRefOid`），M 侧使用结论行记录的**被审 SHA**；报告前必须**重新枚举 T** 并逐对象比对 SHA，任一对象的 SHA 已变化（force-push / 新提交）即该对象**视为未审**，须计入未覆盖清单并重审。
- 已审集合 M = `§9.1` 逐对象结论行中**有明确结论**的对象，且结论行必须取自 `§9.4` **已核对通过的冻结版本**（撰写者临时清单不得作为 M）；只被提到但无结论者**不计入**。
- **对象标识在审查单元清单中必须唯一**（同一对象出现两行 = 重复覆盖，即**不通过**）；`COVERED` 按对象标识**去重后**计数，恒有 `COVERED ≤ TOTAL`。
- 双向差集必须为空：`T - M` 为空（无漏审）、`M - T` 为空（无幽灵对象）；任一非空即**不通过**。差集只证明**枚举一致性**，**不证明**每个对象被独立评审过——独立性由 `§9.1` 的唯一负责人与 `§9.4` 的核对者留档共同取证。
- 结论行必须同时给出**结论类型分解计数**（通过 / 不通过 / 无法判定）与**撰写者、核对者**两名不同人员（**核对者** = `§9.4` 的**独立复验工程师**，与 `§9.4` 所称**复验者**是同一职责视角的两种写法，兼任规则见 `§1`）。
- **未覆盖清单**必须显式列出（无则写"无"）；非空时不得表述为"已全部审查"。
- 最终答复给出 `TOTAL / COVERED / UNCOVERED`、各结论行文件的绝对路径 + 条数 + SHA256、对账命令与原始输出。

### 9.4 产物独立验证（review message 也是实施单元）

- 审查产物（review message / PR 评论 / issue 草稿 / 审计报告 / 通知文案）**一律按实施单元处理**，遵循阶段 3–4：撰写者**不得**担任其复验者。
- 发布前必须由**未参与该审查单元撰写**的**独立复验工程师**（只读）逐条核对：
  1. **证据可复现**：每条发现的位置（`文件:行号` / `PR#` + 提交 SHA）与证据（命令 + 原始输出 / 最小反例 / 原文引用）可被核对者**只读重放**；
  2. **引用准确**：引用的原文、行号、提交、数字与仓库 / PR 现状**逐字段一致**，不得凭记忆复述；
  3. **结论口径一致**：分级符合 `§3` 第 0 条；"通过 / 不通过 / 无法判定"与证据一致；不得把未验证写成已验证；
  4. **无越权表述**：不得包含承诺（"我会合并 / 会修复"）、对他人动机的臆测、未授权的范围扩张；
  5. **可交付性**：读者无需本会话上下文即可理解（对象标识、版本 / 提交、范围、结论）。
- 核对**不通过**时，产物必须整改并**重新核对**；整改由**原撰写者**完成（复验者不得参与整改），整改后必须由同一名独立复验工程师**重新核对**；未核对通过的产物**不得发布**。
- 产物必须先落盘并记录 SHA256 作为核对对象；核对通过后的 SHA256 即**冻结版本**。

### 9.5 发布（对外可见的写操作）

- **发布 = 对外可见的有副作用的写操作**：`gh pr review` / `gh pr comment` / `gh issue create` / 发送通知 / 合并 / 打 tag / 修改远端 / `git push`（使产物离开本机或进入共享位置）。
- 发布须由 **CTO 显式授权**（用户未授权时先展示冻结版本并请求确认），并**逐条留档**：目标（PR / issue / 仓库）、时间、内容 SHA256、执行者。
- **执行者**：发布**必须**由一名**未参与该审查单元撰写与核对**的**高级软件工程师**执行；**不得**指派给 CTO（`§1`：CTO 只读、不改变受版本控制内容与既有行为），CTO 只负责显式授权与留档；**复验者亦不得担任其发布者**（`§1`）。
- **不算发布**：本地 `git commit` 检查点提交（`§8.4`）、在答复或会话内向用户**展示未核对草稿**；但对用户交付的**定稿**、以及任何推送到远端或写入共享位置的产物（含 `git push`）都属于发布，须走 `§9.4` 核对与本节授权。
- 发布内容必须**逐字节等于**已核对通过的冻结版本；发布后内容**冻结**，任何修订都回到 `§9.4` 重新核对。
- **禁止**：产物的撰写者自行发布；复验者自行发布；未核对通过先发布；发布后静默改写；CTO 亲自发布。

### 9.6 汇报（与 §6 叠加）

除 `§6` 第 1–5 项外，必须给出：

1. **审查单元清单与负责人**（对象 → 工程师）；
2. `TOTAL / COVERED / UNCOVERED` 与未覆盖清单；
3. 每个产物的**冻结 SHA256** 与独立复验工程师的结论；
4. **顺序执行证据**（用户要求依次时：对象序列与实际派工时刻）。

## 附录 A · 平台与环境陷阱清单（指导性）

> 本附录为**指导性补充**：正文强制条款优先，条目中的规避做法不解除 §1–§9 任何义务；其中 P9 对应的「共享工作区并发纪律」本身是 §2 阶段 1 的强制条款，此处仅作索引。证据来源：跨 session 审计汇总（cto-flow-audit SUMMARY T2-10 行）。

| # | 陷阱 | 实测失败形态 | 规避做法 |
|---|---|---|---|
| P1 | Windows 混合 shell 引号 | bash 会话里照抄 PowerShell 的 `$_` / `$null` / 反引号续行，或 cmd 的 `2>nul`：变量被 bash 展开成空串，`> nul` / `> $null` 造出**字面名文件** | 命令按当前 shell 方言改写（`shell_flavor` 显式选型）；跨 shell 用 Python 单行；重定向目标写 `/dev/null`（bash）或 `$null`（pwsh），不混写 |
| P2 | CRLF 链 | write 类工具落盘 CRLF；`grep -c $'\r'` 对混合行尾统计失真；`git apply -R` 对 EOL 有损，逆向还原后哈希≠基线 | 落盘后以字节级工具（`od` / Python `open(...,'rb')`）实测行尾再统计；反向还原基线哈希以**落盘实测**为准，不凭推算 |
| P3 | MSYS/Git Bash 路径改头 | 以 `/` 开头的实参被展开成 Git 安装目录前缀（`/sdcard` → `C:/Program Files/Git/sdcard`） | `MSYS_NO_PATHCONV=1` 前缀、双斜杠 `//sdcard`，或该类命令改走原生 PowerShell |
| P4 | `/tmp` 不可达 | Windows 下 `/tmp` 无稳定映射，写临时文件静默落空或落到错误盘符 | 临时/证据文件一律落任务书指定的仓库外目录；不得以 `/tmp` 作约定路径 |
| P5 | exec 静默 clamp | 单条命令实际运行时长被平台静默截断（实测 4m40s 量级），长构建返回截断输出被误读为成功 | 长任务分片执行并写进度文件；对疑似截断的命令用更短定向重跑确认，不把截断输出当完整证据 |
| P6 | pwsh `run:` 块退出码 | 多行脚本块只有**末腿**退出码上传，前腿失败、末腿成功 ⇒ 整体判成功 | 每腿后显式判 `$LASTEXITCODE` / `$?`，腿间用 `&&` 链接，或拆成多条命令逐条验收 |
| P7 | Gradle daemon 内存预算 | 长驻 daemon 叠加大堆参数顶穿宿主内存，构建 OOM/卡死被误判为代码问题 | `gradle.properties` 固定 `org.gradle.jvmargs` 上限；必要时 `--no-daemon`；构建前 `gradlew --stop` 清场 |
| P8 | K/N 测试名禁字符 | Kotlin/Native 测试名含空格/中文/特殊字符时注册失败，测试被跳过造成零执行假绿 | 测试名只用 `[A-Za-z0-9_.-]`；证据必须含 `tests=<N>` 且 N>0（§5 构建证据契约） |
| P9 | 并发工作区构建互相破坏 | 增量缓存 `already registered`、`classes.jar` 截断、共享 `test-results` 被覆盖、`gradlew --stop` 互相打断 | **强制条款**，执行口径以 §2 阶段 1「共享工作区并发纪律」①–⑧ 为准：同波次至多 1 个构建者、默认独立 `git worktree`/仓库外隔离副本、结果同命令快照出仓、`--tests` 用显式类名 |
